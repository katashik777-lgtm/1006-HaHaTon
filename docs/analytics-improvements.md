# Расширенная аналитика

Новые прогоны используют общий bucket_width=0.2 для числовых полей; явно заданные buckets[path] имеют приоритет. Строковые значения сохраняются как категории. Интервалы открыты слева и закрыты справа. Сравнение VALUE, DIFF_FLAG и CHANGE_TYPE не зависит от бакетов. У отсутствующей стороны ADJUSTED остаётся null: это отсутствие поля, а не числовой интервал.

BUCKET_DISTRIBUTION считает строки по атрибуту, версии и бакету. TOTAL — число присутствующих строк этого атрибута в этой версии. BUCKET_TRANSITION публикует только сменившиеся типизированные бакеты. Пары внутри того же бакета входят в TOTAL. TOTAL — число сопоставленных строк атрибута. APP_IDS уникальны, поэтому их количество может быть меньше CNT при массивах. Результаты INFO являются статистикой, а не ошибкой проверки. Отчёт рассчитывается один раз на прогон; повторный вызов в одном Mart кешируется.

Индексы APP_ID и PATH создаются при публикации comparison.duckdb и открываются read-only каждым Mart. На локальной витрине 289533 строк: материализация и индексы 0.466 с; 100 подсчётов по APP_ID 0.056 с. Индексы ускоряют выборочные запросы, но агрегация всей витрины всё ещё читает её целиком. Новый reader не пересоздаёт материализованную таблицу; старые прогоны без comparison.duckdb читаются из Parquet.

Из чтения и нормализации удалено повторное построение DataFrame на каждый файл для встроенного нормализатора. Пакетное построение сохранено. Пользовательские процедуры по-прежнему проверяются отдельно. Полный выигрыш на пользовательском прогоне нужно измерять после повторного запуска: он зависит от диска, числа файлов, массивов и Python-процедур. Предыдущий локальный эксперимент на 4004 файлах (572221 нормализованных строк) показывал 4.11 с последовательного разбора против 1.92 с четырёх процессов, но не учитывал передачу строк и запись Parquet; это не основание обещать такое же ускорение всего приложения.

Качество теперь читается непосредственно из реестра quality, по SOURCE и STATUS, включая parsed; работает и для старых прогонов. Нулевое число ошибок не означает отсутствие данных.

Скоркарты содержат показатели BEFORE/AFTER в соседних колонках. Анализ решений содержит продукт, диапазон Score, стоп-фактор, решение и область около порога ±0.1 включительно. Сторона фильтров выбирается: BEFORE, AFTER, хотя бы одна или обе. Счётчики заявок уникальны; переходы считаются по заявке и продукту. Причины отказа берутся из выбранных продуктовых строк; при выборе сценария используется его расчётная причина.

Два режима стоп-фактора — моделирование, не изменение банковского ответа. Жёсткий режим отклоняет при STOP=true. Мягкий применяет настраиваемый штраф за каждый сработавший стоп-фактор (по умолчанию 0.1); количество хранится в STOP_COUNT. Старые прогоны без STOP_COUNT требуют повторного запуска для моделирования штрафа. Для score<=cutoff штраф увеличивает балл, для score>=cutoff уменьшает. При неизвестных данных результат неизвестен. Близость к порогу считается по исходному Score.

Для появления новых бакетных отчётов нужен новый прогон: опубликованные артефакты не переписываются. При XML/CSV числовые поля должны быть описаны в types профиля — текстовые числа автоматически не угадываются.

Проверки: pytest; node --test frontend/tests/sourceDiff.test.cjs; TypeScript; Vite. Отдельные тесты охватывают JSON, XML, CSV и изменение 0.42→0.58 внутри одного бакета. Четыре теста изоляции пропущены окружением, а не объявлены пройденными.
