# Установка и эксплуатация без Docker

Пакет предназначен для отдельного каталога `/opt/spr`, пользователя `spr` и данных `/var/lib/spr`. Шаблоны в `deploy/` подготовлены, но на удалённом сервере не проверены. SSH-реквизиты не предоставлены; соединение с адресом из исходного документа не выполнялось.

Перед установкой проверьте ОС, память, диск, занятые порты 80/443/8765 и действующие службы. Не заменяйте существующий reverse proxy; добавьте отдельный виртуальный хост. Нужны Python 3.12+, venv, bubblewrap и Caddy (либо настроенный администратором HTTPS reverse proxy).

1. Создайте системного пользователя `spr` без интерактивного входа. Разместите код в `/opt/spr`, данные в `/var/lib/spr` с владельцем `spr:spr` и правами 0700. Код после установки должен быть доступен службе только для чтения.
2. Создайте `/opt/spr/.venv`, установите `requirements.txt`. Готовый `frontend/dist` входит в репозиторий.
3. Создайте `/etc/spr.env` из `.env.example`, права 0600. Укажите реальный `BASE_URL`, `SPR_DATA=/var/lib/spr`, `POLARS_MAX_THREADS=4`. Для PostgreSQL задайте DATABASE_URL с драйвером `postgresql+psycopg` и отдельным пользователем БД.
4. С теми же переменными выполните от пользователя `spr`: `.venv/bin/python -m spr.cli init`. Пароль задаётся интерактивно, в аргументы командной строки его не передавайте.
5. Установите `deploy/spr-api.service` и `deploy/spr-worker.service` в `/etc/systemd/system`. Выполните `systemctl daemon-reload`, затем `systemctl enable --now spr-api spr-worker`.
6. Настройте DNS, подставьте домен в Caddyfile, проверьте конфигурацию перед перезагрузкой Caddy. Caddy получает и обновляет TLS-сертификат. Не открывайте порт 8765 наружу.
7. Проверьте `/api/health`, `/api/ready`, вход, обработку и изоляционные тесты под тем же UID и ограничениями службы. Bubblewrap требует разрешённых user namespaces; наличие бинарного файла не гарантирует успешный запуск. До прохождения тестов публичное исполнение Python не подтверждено.

Службы пишут журналы в journald. Настройте предел `SystemMaxUse` и срок хранения в конфигурации journald согласно политике сервера; не переписывайте глобальную конфигурацию без проверки текущих служб. API и worker автоматически перезапускаются, просроченные задания повторно захватываются по lease (не более трёх попыток).

## Резервирование SQLite

Остановите **обе** службы и любые CLI-импорты. Текущая команда резервирования требует окна обслуживания, иначе файлы и БД могут попасть в разные поколения.

```bash
systemctl stop spr-api spr-worker
# Выполнять от spr, с SPR_DATA=/var/lib/spr и доступом к каталогу копий:
/opt/spr/.venv/bin/python -m spr.cli backup /srv/backups/spr-YYYYMMDD-HHMM
systemctl start spr-api spr-worker
```

Путь назначения не должен существовать и должен находиться вне SPR_DATA. Копия содержит SQLite, sources, artifacts и SHA-256 каждого файла. При нестандартном SQLite DATABASE_URL встроенная команда не поддерживается; используйте стандартную БД в SPR_DATA.

Восстановление выполняйте в **новый пустой каталог** SPR_DATA, без запущенных служб. Команда `python -m spr.cli restore /srv/backups/КОПИЯ` проверяет хеши, копирует данные и переносит ссылки управляемых файлов на новый корень. После восстановления проверьте manifest, вход и старый отчёт; затем переключите SPR_DATA служб. Оригинальную копию сохраняйте до проверки.

PostgreSQL: встроенная команда резервирования отклоняет этот режим. При остановленных писателях необходимы `pg_dump` и копия всего SPR_DATA одного поколения; восстановление и перенос путей PostgreSQL пока требуют отдельной реализации/проверки. Не считать эту конфигурацию проверенной для эксплуатации.

## Обновление и откат

Сохраните проверенную резервную копию и текущую версию кода. Остановите службы, обновите отдельный каталог выпуска, установите зависимости, примените `python -m alembic upgrade head`, затем запустите службы и проверьте readiness и существующий отчёт. При несовместимой миграции возвращайте вместе прежний код и согласованную копию данных; понижение схемы без проверки не выполняйте.
