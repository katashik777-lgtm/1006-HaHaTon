# Пояснительная записка

**Скорифай · команда 1006**

В модулях 3 и 4 Скорифай сравнивает ответы двух версий системы принятия решений (СПР) по одним заявкам. Аналитик может пройти от числа в сводной до изменённого поля и исходных ответов до и после смены стратегии.

## 1. Стек и архитектура

React и TypeScript отвечают за интерфейс, FastAPI — за права доступа и приём заданий. Отдельный Python-обработчик строит отчёты в фоне. Polars сравнивает колоночные данные, DuckDB обслуживает сводную и детализацию. Интерфейс запрашивает ход расчёта и восстанавливает состояние по сохранённому заданию после перезагрузки.

## 2. Хранение и сравнение

SQLite локально и PostgreSQL на Railway хранят пользователей, роли, конфигурации, задания и аудит. Исходные файлы сохраняются с SHA-256, результаты — в Parquet. Профиль задаёт сопоставление по ID заявки, пути и ключу элемента массива. Для каждого поля фиксируется одно из четырёх состояний — совпало, изменилось, появилось или исчезло.

## 3. Фоновая обработка и восстановление

Обработчик атомарно забирает задание, продлевает аренду и пишет результат во временный каталог. Публикация происходит атомарным переименованием после сверки манифеста. При восстановлении готовый результат проверяется повторно. На Railway сравнение идёт партиями по 200 заявок, что ограничивает размер промежуточного объединения таблиц.

## 4. Процедуры и проверки

Прогон сохраняет версии входов, профиля, кода и параметров. Комплектные проверки подключаются через интерфейс `CHECK` и получают данные через `MartAPI`. На Railway выполнение ограничено по времени, файловому доступу и сети с помощью Landlock и seccomp. Для локальной проверки комплекта доступен доверенный режим Python.

## 5. Догрузка и отчёты

После догрузки новый прогон строит отдельный отчёт. Неполные и повреждённые пары попадают в отчёт качества. Сводная считает уникальные ID, а детализация применяет те же фильтры. Из отдельного отчёта проверок можно открыть затронутые заявки.

## 6. Результат и замеры

Обработаны 4 004 файла и 2 002 пары. **502 заявки с различиями** совпали с эталоном по набору ID, у 385 изменилось решение. Пять проверок дали 32 результата (2 PASS, 30 FAIL по правилам) без ошибок исполнения. На Apple M4 с 16 ГиБ полный расчёт занял 5,33 с, из них чтение и нормализация — 3,09 с. Сводная с открытием DuckDB — 20,77 мс медиана и 30,64 мс p95 за 20 повторов без учёта сети и интерфейса.

## 7. Ограничения и следующий шаг

После догрузки пересчитывается весь набор. Подключение к банковской СПР требует адресов и проверки контракта обмена. Следующие шаги — замер пикового потребления памяти при одновременной работе пользователей и пересчёт только затронутых заявок.
